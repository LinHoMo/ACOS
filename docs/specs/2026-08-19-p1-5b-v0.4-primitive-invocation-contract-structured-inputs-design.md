# P1-5B v0.4 — Primitive Invocation Contract & Structured Inputs 实验设计（spec DRAFT）

> **状态**: DRAFT（待用户审批 → APPROVED → FROZEN；冻结前内容可修改）。
> **日期**: 2026-08-19 · **代码版本**: main @ `f613592`（P1-5B v0.3 FROZEN / H-C NOT SUPPORTED）。
> **动机**: v0.3 有效负结果暴露两个**独立失败类**——序列化契约（Failure A）与运行时绑定契约（Failure B）。二者必须分开实验，不能合并为一次"Prompt Improvement"。

---

## 1. 核心问题

> **模型生成的步骤，如何可靠地调用一个 Primitive，而不需要猜测其底层序列化格式和运行时变量环境？**

这比 Prompt 优化更重要：如果 Cognitive Primitive 的输入/输出/执行环境没有足够强的**机器契约**，LLM 生成的"程序"再漂亮，也只是看起来像程序的文本。

**长期架构对象（本设计的定义）——Primitive Invocation Contract**：

```text
Primitive Invocation Contract = 序列化契约（step 如何把参数写进 Plan IR）
                              × 执行绑定契约（运行时如何把数据注入代码执行环境）
```

它是 ACOS 下一阶段（Phase 2 structured transport）的稳定接口面：v0.4 验证其最小子集，为将来迁移到 stdin/JSON structured transport 铺路。

## 2. v0.3 已证明的两个独立失败类

### Failure A：序列化契约（Serialization Contract）

模型生成（对象形式）：

```json
{
  "code": {
    "path": "${item}"
  }
}
```

CIR 要求（JSON 字符串形式）：

```json
{
  "code": "{\"path\": \"${item}\"}"
}
```

结果：`CIR schema mismatch: invalid type: map, expected a string`。**3 次 repair 全部重犯同一错误**（C 组 4/5 编译失败）。这不是 Capability Discovery 问题，是 **LLM ↔ Plan IR 的序列化契约没有被模型正确理解**。

### Failure B：运行时绑定契约（`env`）

所有可执行样本（B 5/5、C 1/1）均失败于：

```text
NameError: name 'env' is not defined
```

与 schema discovery 无关——`inspect_schema` 再强也解决不了 `env` 不存在的问题。

## 3. 两个独立子假设（不合并）

### H-S：Serialization Contract Hypothesis

> 明确规定 `code` 是 JSON string（而非 object），并提供最小正例，能否消除 code-as-map 编译失败？

### H-E：Structured Execution Binding Contract Hypothesis

> 以结构化 `inputs` 作为推荐的 Primitive 执行绑定接口（完整 Package = inputs 注入 + inputs 教学 + env 拒绝），并禁止新的 `env` 使用，能否消除 `env` 类失败，并将失败前沿推进到真正的程序设计问题？

> **措辞说明**：H-E 测试的不是单一的"inputs injection"，而是完整的 Structured Inputs Package（§7 因子定义）；命名与因子定义保持一致。

## 4. 序列化契约（code 字符串规范）

Plan IR 中 `code` 的正式规范：

```text
code:
  type: string
  format: python-source
```

- `code` 在 Plan IR 中**始终是 JSON 字符串**；运行时再按 Primitive Contract 解释（JSON 字符串 → 参数对象）。
- Prompt 教学必须给**最小正例**（不得塞完整旗舰任务范例，防止污染 Program Discovery）：

```json
{
  "code": "print('hello')"
}
```

```json
{
  "code": "path = '${item}'\nprint(path)"
}
```

## 5. 结构化 inputs 最小接口（Structured Inputs）

CIR 现有 `execute_python` 节点结构不变（`code: string` + `inputs: map`，inputBindings 已编译进 inputs）；只改**运行时传输语义**：

```text
CIR
  ↓
execute_python
  ├── code: string
  └── inputs: structured values（绑定解析后的 JSON 值）
```

运行时执行 Python 时注入：

```python
import os, json
inputs = json.loads(os.environ.get('ACOS_PYTHON_INPUTS', '{}'))
```

模型代码示例（S2/S3 教学）：

```json
{
  "code": "print(inputs['file_path'])",
  "inputBindings": [
    { "param": "file_path", "source": "inspect_all", "binding": "all_schemas" }
  ]
}
```

原则：

> **Runtime values should cross stage boundaries as structured data, not source-code interpolation.**

- `inputs` 为保留名；其值为 node 的已解析 inputs（除 `code` 外），经 JSON 注入（Record/List → 真实 Python 结构）。
- `${...}` 源码插值**保留可用**（兼容既有合法用法），但不再是教学推荐路径。
- 与 Stage Data Contract 的 `inputTypes` 思维一致；未来可无缝迁移到 stdin/JSON transport。

## 6. env 迁移/兼容策略

| 项 | 策略 |
|---|---|
| 历史 trace 重放 | Runtime 保留旧 `env` 注入代码路径，仅用于 v0.2/v0.3 冻结 trace 的归档可执行性（不参与 v0.4 实验） |
| v0.4 新 run（S0/S1） | **不注入 `env`**（与 v0.3 运行时一致）——S0/S1 是对照臂，env 行为必须与 v0.3 完全一致，否则无法归因 |
| v0.4 新 run（S2/S3） | 编译期扫描生成代码中的 `env` 使用（`\benv\s*[\[.]` 等启发式）→ **InvalidPythonBinding** 错误类（编译失败，进入 repair 循环）；**杜绝新生态固化错误 API** |
| 错误类 | 新增 `InvalidPythonBinding`（S2/S3 编译期）；`DeprecatedRuntimeBinding` 预留为降级警告通道（本期不使用） |

**设计决策标注（需用户确认）**：env 拒绝仅作用于 S2/S3 臂（作为 structured inputs 因素的组成部分）；S0/S1 保持 v0.3 语义（env 容忍、不注入 → NameError 继续出现），以维持因素隔离。若用户希望 env 拒绝全局生效，则 S1 将同时包含"序列化教学 + env 拒绝"两个变化，因素矩阵需重排。

## 8. 指标

沿用四层矩阵（Compile / Contract / Execute / Adequacy，×4 组），并新增（分母为 0 → **N/A**，不得记 0%）：

- **serialization_failure_rate**：`code-as-map 类编译失败 run / total runs`（错误特征：`invalid type: map, expected a string` / `expected a map`）
- **env_failure_rate**：`env 类失败 run / 含 execute_python 的 run`（S0/S1：运行时 `NameError: env`；S2/S3：编译期 `InvalidPythonBinding` 未被修复导致最终编译失败）
- **env_persistence_rate**：`最终编译产物（final plan/CIR）中仍含 env 引用的 run / 含 execute_python 的 run`（S2/S3 反映模型是否学会放弃 env）
- **repair_rate / repair_attempts**：repair 触发率与平均次数（对比 v0.3：A 0.60 → B 2.00 → C 2.80）
- 代码缺陷分类沿用 v0.3：`NameError / KeyError / SyntaxError / RuntimeContractViolation / SchemaAssumption / Other`，新增 `InvalidPythonBinding` 类

## 9. 成功标准（阈值暂定，随 APPROVED 固化）

- **H-S 支持**：`serialization_failure_rate(S1) ≤ 0.2`（S0 = 0.8，要求相对下降 ≥ 60%）。
- **H-E 支持**：`env_failure_rate(S2) ≤ 0.2` ∧ `env_persistence_rate(S2) ≤ 0.2`。历史 v0.3 C（S0）基线（frozen traces 实测，commit `f613592`）：`env_failure_rate = 1/1 = 100%`——唯一可执行样本 run-001 因 `env` NameError 失败，其余 4/5 编译失败、final plan 无 execute_python 步骤，按指标定义不计入分母；`env_persistence_rate = 1/1 = 100%`——run-001 final plan 代码含 `env[...]`。即要求 S2 相对 S0 相对下降 ≥ 80%（绝对 ≤ 0.2）。
- **S3 交互**：若 `Compile(S3) ≥ 80%` 且 Execute/Adequacy 不劣于 max(S1, S2) → 两因素正交互补，支持合并为完整 Primitive Invocation Contract。
- **与命题 B 完全解耦**：H-S/H-E 达标只支持各自中间命题，**不宣布命题 B**（多任务长期问题）。

## 10. 工程范围（最小化）

- Prompt 教学段：§4 序列化段（2 个最小正例）+ §5 inputs 段（1 个绑定示例）——均为纯文本段，不新增 capability。
- 运行时：`execute_python` 注入 `inputs`（ACOS_PYTHON_INPUTS + prologue）；保留 `${...}` 插值；保留 env 注入代码路径（archive-only）。
- 编译器：python 代码 env 启发式扫描 → `InvalidPythonBinding`（S2/S3 模式开关）。
- **不修改**：Plan IR schema、Plan→CIR 编译器、契约 R1–R5、runtime 信封语义、csv 能力实现、v0.3 历史数据（全部冻结）。
- 不新增 capability、不重跑 A/B/C、不重定义命题 B、不给 csv.aggregate 加任何教学。
