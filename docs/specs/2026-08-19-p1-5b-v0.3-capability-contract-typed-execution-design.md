## 1. 核心问题

> `execute_python` 一个 primitive 要求模型同时理解太多隐含上下文：
>
> ```text
> Python runtime contract + 数据 schema + 列名 + 异常处理 + 模板插值
> ```
>
> 把"运行时 API 手册塞进 System Prompt"不是目标架构。目标是把模型需要猜的执行细节**从 Prompt 移回 Primitive Contract / Runtime**。

**v0.3 命题（正式命名：Capability Contract Hypothesis，H-C）**：

> **H-C**：Primitive Contract 的信息边界设计，是 ModelCompiler 能否可靠工作的关键变量——capability 提供 schema（而非模型猜 schema）时，端到端成功率上升。

H-C 是**中间工程命题**，与命题 B（自动发现认知程序）是两个层次，不得混为一谈：H-C 只测"给模型更准确的能力边界是否提升程序执行可靠性"；即使 H-C 成立，命题 B 仍需在更多任务上另行验证。

## 2. 能力分层（本设计采用的三层模型）

```text
High-Level Cognitive Capability     （认知意图：csv.inspect_schema / csv.validate / csv.aggregate）
        ↓
Structured Operation                （结构化参数：metrics / filters / thresholds）
        ↓
Low-Level Runtime                   （确定性实现：execute_python 等低级原语，模型不可见）
```

| 层 | 模型写什么 | 模型不需要知道 |
|---|---|---|
| 现状 `execute_python` | `pd.read_csv("${file_path}"); df["quantity"]` | schema、Python 环境、变量注入、列名、容错 |
| v0.3 `csv.aggregate` | `{ file: ${file_path}, metrics: [revenue_sum, row_count, issue_count] }` | 全部——实现是确定性的 |

**插件生态愿景**（编译器按任务选择能力，而非 LLM 发明低级实现）：

```text
CSV Plugin      { inspect_schema, validate, normalize, aggregate }
Database Plugin { inspect_schema, query, aggregate }
Python Plugin   { execute }
```

## 3. 因果实验（只做一个小 Primitive）

### 新增 capability：`csv.inspect_schema`

返回（确定性实现，stdout JSON）：

```json
{
  "columns": [{"name": "revenue", "type": "number"}, {"name": "quantity", "type": "integer"}],
  "row_count": 120,
  "issues": ["field_count_mismatch", "missing_value"]
}
```

### 实验分组（A/B/C 对照，×5 每组，同 v0.1/v0.2 条件）

> **数据批次声明**：A 组 = **历史冻结数据**（v0.2 `formal-eval-v0.2-results/` 的 5 条 traces，commit `7a3b36a`），**不是本轮重新采样的数据**；B/C 组为本轮新采样 ×5。报告中必须区分批次，读者不得将 A/B/C 视为同批次随机化运行。

| 组 | 变化 | 模型如何获得 schema | schema 是否被强制执行 |
|---|---|---|---|
| **A（frozen control）** | v0.2 现状（`execute_python`，全自动） | 猜 | 否 |
| **B** | 仅新增 `csv.inspect_schema`（其余不变：Plan IR 编译器、prompt、模型、任务） | 观察（Plan 先 inspect，再依据真实 schema 生成后续步骤） | 否（是否使用取决于模型） |
| **C** | **Runtime/Primitive-level schema enforcement**：新 capability（如 `csv.aggregate`）在运行时校验其 field 引用，非法列名 → PrimitiveFailure 拒绝执行（**Primitive 自己执行校验，非编译期静态检查**） | 强制 | 是（运行时/primitive 层） |

**C 组边界声明**：C 组是 **Runtime/Primitive-level schema enforcement**——校验发生在 primitive 实现内部（schema 校验 → Accept/Reject）。**不包含、也不宣称 Compile-time static enforcement**（那需要编译器支持动态 schema，属于后续工作；与"Plan IR / 编译器 / 契约零改动"的实验边界一致）。

### 指标

- 沿用四层：Compile / Contract / Execute / Adequacy
- 新增（正式定义，分母为 0 时记 **N/A**，不得记 0%）：
  - **inspect_usage_rate**（B 组）：`inspect_requested / total_plans`（模型在 Plan 中引用 inspect 步骤数 ÷ Plan 总数）
  - **inspect_executed / inspect_result_consumed**（B 组）：细分——调用了 inspect ÷ 调用后其输出被后续步骤 data_flow 引用（`inspect_used = true/false` 第一版即可）
  - **Schema utilization rate**（B 组）：`inspect_schema 返回的信息被后续 Plan/CIR 实际引用或影响的数据点比例`（第一版简化为 `inspect_result_consumed / inspect_executed`）
  - **Schema hallucination rate**：`invalid_field_references / all_field_references`（代码中引用的全部列名作分母，其中不存在于实际 schema 的作分子；**无列名引用 → 0/0 → N/A**，防止"没猜所以没幻觉"被误读为 0%）
  - **Code defect rate**：`defective_execute_python_steps / total_execute_python_steps`，并按类统计：`NameError / KeyError / SyntaxError / RuntimeContractViolation / SchemaAssumption / Other`
  - **Repair rate**（repair 触发率与平均次数，对比 v0.2 0.6/run）

### 成功标准（不预设）

- 若 B 或 C 的 Execute/Adequacy 显著高于 A → 支持 H-C（Primitive 信息边界是关键变量）。
- 若 B 无改善而 C 改善 → 观察式能力不够，需强制式 schema 执行（primitive 层接管）。
- 若 B/C 均无改善 → Primitive 契约不是瓶颈，转向数据/任务表征层。

## 4. 工程范围（最小化）

- 新增 `csv.inspect_schema` primitive（确定性实现，纯 stdlib CSV 解析，复用 v0.2 冒烟验证的清洗逻辑子集）。
- 注册进 ALLOWED_CAPABILITIES + PLAN_SYSTEM_PROMPT 能力清单（一行教学：能力名 + 返回结构）。
- Plan IR / 编译器 / 契约 / 运行时信封语义：**零改动**（新能力作为普通 primitive 步骤编译）。
- 实验 B 的 Plan 会自然生成 `inspect → ... → aggregate` 数据流（模型看到 inspect 输出再规划）。

## 5. 判定（H-C 复查路径，不与命题 B 混淆）

- 若 C 组 Adequacy ≥ 60% ∧ Compile ≥ 80%：**H-C 支持**（typed capability boundary 显著提升可执行性）——**只支持 Capability Contract 中间命题，不直接宣布命题 B 成立**（强制 schema 压下的执行错误不代表通用程序发现能力；命题 B 需后续在更多任务上验证）。
- 若 B 组达到同样标准：进一步支持"模型可自主使用 capability 契约"（更强的自动发现，但仍不直接证明命题 B）。
- 否则 H-C 维持不支持，v0.4 方向：任务→能力映射的确定性选择（compiler picks plugin by task type）。
