# P1-5B v0.3 — Capability Contract & Typed Execution 实验设计（spec DRAFT）

> **状态**: DRAFT（待用户批准冻结）。
> **日期**: 2026-08-19 · **代码版本**: main @ `7a3b36a`（P1-5B v0.2 FROZEN）。
> **动机**: P1-5B v0.2 有效负结果——Plan IR + 确定性编译消除了结构性失败（Compile 20%→80%、binding closure 100%），失败前沿移到**模型生成的 `execute_python` 步骤代码**：模型必须自己猜 Python runtime 契约（无预置全局、`${...}` 插值语义）、数据 schema 与列名（run-005 `KeyError: 'quantity'`）、异常处理。这不是"再写 20 条 Prompt 规则"能解决的——它暴露的是 **Primitive 粒度/信息边界**问题。

---

## 1. 核心问题

> `execute_python` 一个 primitive 要求模型同时理解太多隐含上下文：
>
> ```text
> Python runtime contract + 数据 schema + 列名 + 异常处理 + 模板插值
> ```
>
> 把"运行时 API 手册塞进 System Prompt"不是目标架构。目标是把模型需要猜的执行细节**从 Prompt 移回 Primitive Contract / Runtime**。

**v0.3 命题（中间命题候选）**：

> Primitive Contract 的信息边界设计，是 ModelCompiler 能否可靠工作的关键变量——capability 提供 schema（而非模型猜 schema）时，端到端成功率上升。

## 2. 能力分层（本设计采用的三层模型）

```text
High-Level Cognitive Capability     （认知意图：csv.inspect_schema / csv.validate / csv.aggregate）
        ↓
Structured Operation                （结构化参数：metrics / filters / thresholds）
        ↓
Low-Level Runtime                   （确定性实现：execute_python 等低级原语，模型不可见）
```

| 层 | 模型写什么 | 模型不需要知道 |
|---|---|---|
| 现状 `execute_python` | `pd.read_csv("${file_path}"); df["quantity"]` | schema、Python 环境、变量注入、列名、容错 |
| v0.3 `csv.aggregate` | `{ file: ${file_path}, metrics: [revenue_sum, row_count, issue_count] }` | 全部——实现是确定性的 |

**插件生态愿景**（编译器按任务选择能力，而非 LLM 发明低级实现）：

```text
CSV Plugin      { inspect_schema, validate, normalize, aggregate }
Database Plugin { inspect_schema, query, aggregate }
Python Plugin   { execute }
```

## 3. 因果实验（只做一个小 Primitive）

### 新增 capability：`csv.inspect_schema`

返回（确定性实现，stdout JSON）：

```json
{
  "columns": [{"name": "revenue", "type": "number"}, {"name": "quantity", "type": "integer"}],
  "row_count": 120,
  "issues": ["field_count_mismatch", "missing_value"]
}
```

### 实验分组（A/B/C 对照，×5 每组，同 v0.1/v0.2 条件）

| 组 | 变化 | 模型如何获得 schema |
|---|---|---|
| **A（frozen control）** | v0.2 现状（`execute_python`，全自动） | 猜 |
| **B** | 仅新增 `csv.inspect_schema`（其余不变：Plan IR 编译器、prompt、模型、任务） | 观察（Plan 先 inspect，再依据真实 schema 生成后续步骤） |
| **C** | schema-aware execution：编译器/primitive 强制 schema（步骤输入类型由 inspect 输出驱动；非法列名在编译期/执行期拒绝而非模型猜测） | 强制 |

### 指标

- 沿用四层：Compile / Contract / Execute / Adequacy
- 新增：
  - **Schema hallucination rate**（生成代码中引用的列名不存在于实际 schema 的比例）
  - **Code defect rate**（execute 层 Python 代码缺陷比例：NameError / KeyError / 语法错误 / 假设错误）
  - **Repair rate**（repair 触发率与平均次数，对比 v0.2 0.6/run）

### 成功标准（不预设）

- 若 B 或 C 的 Execute/Adequacy 显著高于 A → 支持"Primitive 信息边界是关键变量"命题。
- 若 B 无改善而 C 改善 → 观察式能力不够，需强制式 schema 执行（编译器/运行时接管）。
- 若 B/C 均无改善 → Primitive 契约不是瓶颈，转向数据/任务表征层。

## 4. 工程范围（最小化）

- 新增 `csv.inspect_schema` primitive（确定性实现，纯 stdlib CSV 解析，复用 v0.2 冒烟验证的清洗逻辑子集）。
- 注册进 ALLOWED_CAPABILITIES + PLAN_SYSTEM_PROMPT 能力清单（一行教学：能力名 + 返回结构）。
- Plan IR / 编译器 / 契约 / 运行时信封语义：**零改动**（新能力作为普通 primitive 步骤编译）。
- 实验 B 的 Plan 会自然生成 `inspect → ... → aggregate` 数据流（模型看到 inspect 输出再规划）。

## 5. 判定（命题 B 复查路径）

- 若 C 组 Adequacy ≥ 60% ∧ Compile ≥ 80%：命题 B **支持**（在 typed capability 边界内自动发现可执行认知程序成立）。
- 若 B 组达到同样标准：进一步支持"模型可自主使用 capability 契约"（更强的自动发现）。
- 否则维持不支持，v0.4 方向：任务→能力映射的确定性选择（compiler picks plugin by task type）。

## 6. 冻结清单（批准后生效）

- 任务/数据集/GT/oracle/模型/超时：与 v0.1/v0.2 相同
- Plan IR schema、Plan→CIR 编译器、契约 R1–R5、runtime 信封语义：与 v0.2 FROZEN 相同（零改动）
- v0.2 历史数据不修改（SUCCESS-006 已冻结）
- 新增仅限：`csv.inspect_schema` primitive + 能力注册 + A/B/C harness（`formal-eval-v0.3.ps1`，A 组复用 v0.2 traces 作为 frozen control）

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 模型不用 inspect（继续猜） | 实验 B 单独统计 inspect 使用率；若普遍不用 → C 组强制路径 + prompt 中能力存在性教学（非 API 手册） |
| inspect 本身成为新失败点 | 确定性实现 + 冒烟测试；失败分类记录 |
| 实验膨胀 | 冻结范围：只加 1 个 primitive，A 组直接复用 v0.2 数据（0 额外成本） |
